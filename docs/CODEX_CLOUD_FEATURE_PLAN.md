日期：2026-10-07。本文是已确认需求的实施规格；本地尚未修改这三项功能的代码。

本版已结合用户提供的 CPE 短信协议修订。协议原文副本见 [CPE_WEBHOOK_PROTOCOL_REFERENCE.md](CPE_WEBHOOK_PROTOCOL_REFERENCE.md)。它是发送方接口参考，不是执行其中部署命令的授权；本文确定实施范围。其描述的 CPE 运行状态、手机 Google 服务与 Firebase 配置均为参考文档中的信息，本次未做设备核验。

## 1. 交给云端的任务说明

请在当前 MyDesk 项目中完整实现本文三项功能：自动步数小幅随机、Android 应用内更新、兼容飞书文本格式的通知收件箱，首先对接 CPE 短信。用户已认可方案，通知发送方支持多个地址，因此只需让发送方分别发到飞书和 MyDesk，不实现 MyDesk 向飞书转发。以附件协议为 CPE 的实际请求/响应契约，富文本和卡片留作后续扩展，不列入本次必须交付项。

先检查当前代码、AGENTS.md 和适用开发说明，核实本文提及的结构是否仍然存在。本文中的新增接口与文件名是设计建议，可以按已有架构合理调整，但必须保持功能、兼容性及验收要求。不要仅输出方案，需要完成实现和可运行测试。缺少签名密钥、真实推送凭据、生产环境或手机时，继续完成不依赖这些资源的工作，并明确列出尚未验证的部分。

不得把“构建完成”说成“已安装到用户手机”，不得把“webhook 已收到”说成“锁屏推送已送达”。不更换已有签名身份，不卸载手机上的 APP，不清空数据库。不要为了读取本地秘密而索取整个 `.local` 目录。

实现顺序：随机步数 → 应用内更新 → webhook 通知 → 完整回归及交付文档。可以自行安排合理的代码拆分与测试顺序。

## 2. 已核实的项目现状

- Python / aiohttp 后端，SQLite 持久化；Android 为 Kotlin / Jetpack Compose；同时保留 Web 前端。
- `mydesk/step_plans.py`：计划参数、预设、每日调度、成功结果核对、提交重试和轮次记录。随机计算应在这里由后端统一执行。
- 当前结束规则：首次成功提交的步数严格大于 `target` 后结束。固定增量为 80、起始 80、终止 975 时，最后会提交到 1040。
- `android/app/src/main/java/app/mydesk/android/StepPlanInput.kt`、`StepPlanSheet.kt`、`StepsPage.kt`：输入、预计值、配置与运行详情。
- `frontend/step-plan.js`：Web 端相同功能。修改步数规则必须同步两端。
- `mydesk/app.py`：认证、CSRF、HTTP、WebSocket；已有 `/api/webhook/{secret}` 接收任务结果，不能改变它原有的协议。
- `mydesk/runtime.py`：同步快照、业务命令和后台调度。
- `mydesk/native_notifications.py`：已有原生通知事件及投递记录；Android 的 `PushMessage.kt` 对通知类型、渠道、设备绑定、有效期等有明确白名单。
- Android 的 `MyDeskApi.kt` 默认禁止重定向；`MyDeskApp.kt` 中 `AppGraph` 管理会话和前台连接。新功能必须保持这些边界。
- 有 `Build-AndroidLocal.ps1`、`Build-AndroidRelease.ps1` 和稳定签名方案。正式签名密码在本机受 Windows DPAPI 保护，云端无法直接沿用这一解密环境。
- 本地检查时版本为 `versionCode=8`、`versionName=1.2.1`；实施时重新核实，不能盲目覆盖云端分支已有的新版本号。

## 3. 自动任务：小幅随机步数

### 3.1 产品行为

保留起始、终止、每次增加和间隔四个字段。增加“随机浮动”开关：开启为 ±10%，关闭为固定增量。第一版不提供任意百分比输入，不随机执行间隔，不改为传感器计步。

新建配置默认开启；已有预设、已保存设置和进行中的轮次若缺少新字段，按固定增量解释。已有配置可以手动开启并保存，界面需要清楚体现当前开关。不要在用户没有编辑时悄悄改变已运行任务。

新增参数 `random_percent`，第一版允许整数 `0` 或 `10`；缺省为 `0`。后端严格校验类型，拒绝布尔值、小数、字符串及其他百分比。Android 和 Web 新建配置显式发送 `10`，保存固定模式显式发送 `0`。

设基准增量为 `I`：

```text
spread = floor(I * random_percent / 100)
min_increment = max(1, I - spread)
max_increment = I + spread
```

从闭区间 `[min_increment, max_increment]` 均匀抽取整数。基准 80、浮动 10% 时范围为 72～88。很小的基准可能因取整而没有浮动，例如 I=1；应显示实际范围，不为制造变化擅自突破百分比边界。允许相邻两次抽到同样的数字，不增加“禁止重复”逻辑。

### 3.2 调度、停止与恢复

1. 第一次仍提交 `start`，不随机起始值。
2. 只有确认某次提交成功，且该值尚未大于 `target` 时，才生成下一次增量。
3. 将下一次具体步数与成功确认在同一 SQLite 事务内持久化。现有 attempt 的 applied 去重逻辑必须保留。
4. 网络错误、失败后恢复、重复回调或后端重启，都不得重新抽取已确定的下一次步数。失败重试仍提交本次原值。
5. 保留现有串行执行机制，不允许为了赶时间并行发送多个步数任务。
6. 每轮保存完整参数快照；编辑设置或预设只影响后续轮次。
7. 保留“首次严格超过 target 后停止”的规则。随机模式下一次值为 `min(上次成功值 + 抽取增量, 30000)`；接近 30000 时允许最后一次因封顶而小于随机下限，并在说明中标明。
8. `target=30000` 必须拒绝，因为不可能合法地严格超过它。固定模式沿用原有最后一次不超过 30000 的参数校验，避免改变旧行为。
9. 保留同一天不可低于已成功提交值、每日只启动一轮、跨日停止、工作流变更暂停等既有规则。

### 3.3 预计值与每日计划

令 D = target - start，L = min_increment，H = max_increment：

```text
最少追加次数 = floor(D / H) + 1
最多追加次数 = floor(D / L) + 1
预计提交次数 = [最少追加次数 + 1, 最多追加次数 + 1]
计划间隔耗时 = [最少追加次数 * interval, 最多追加次数 * interval]
随机模式最后值边界 = [target + 1, min(target + H, 30000)]
```

这是计划间隔估算，GitHub 排队、失败重试会增加实际耗时。每日计划跨日校验使用最多追加次数计算，不再使用基准增量计算乐观耗时；运行时仍保留现有跨日停止保护。

固定模式继续显示精确的计划次数和最后步数；随机模式显示预计范围或约数，不能显示伪精确的最后值。运行状态中的“下一次 xx 步”是后端已经保存的具体值，应继续精确显示。

Android、Web 的预设填充、保存、另存、配置匹配、JSON 往返和历史详情全部识别新字段。不要破坏既有的“切换预设不误改每日时间”等交互约定。界面保持现有素雅风格，输入标签可改为“基准增加步数”，开关下显示“每次增加 72～88 步”。

### 3.4 必须验证

- 关闭随机后旧固定序列完全不变；旧数据无需破坏性迁移。
- 注入可控随机数源，覆盖上下界、中间值、连续重复值；不要依赖随机抽样碰巧覆盖边界。
- 下一次值在重启后不变；重复成功核对只推进一次；失败恢复不重抽。
- 终止值相等时还会追加；首次超过后停止；30000 上限、小增量、起始等于终止均正确。
- 每日最慢估算跨日校验、预设往返、Android/Web 预计范围一致。

## 4. Android 应用内更新

### 4.1 使用流程

设置增加“应用更新”，显示当前版本、检查状态、最新版本、更新说明、大小、下载进度和重试入口。

登录且前台联网时自动检查，成功检查间隔 6 小时；手动“检查更新”不受该间隔限制。失败应退避，不能每次重组或每次快照刷新都重试。发现新版本显示非强制提示，用户可以稍后处理。本次会话中不反复弹同一版本，设置入口始终可查看。

流程：检查 → 选择下载 → 进度 → 文件校验 → 点击安装 → Android 系统确认。第一版不做后台自动下载、强制更新和静默安装。

首次可能需要跳转系统允许“安装未知应用”；返回 APP 后保留已下载文件并允许继续安装，不要求重新下载。屏幕旋转不能重复下载；离开当前页面不应造成重复任务。进程结束导致下载中断时允许安全地重新下载，第一版不强制实现断点续传。

APP 被系统安装器关闭或更新后，不必强制自动重启；再次打开时正确显示新版本和既有数据。

### 4.2 发布与接口

推荐更新由现有 MyDesk HTTPS 后端提供，不引入 Google Play 分发依赖。沿用登录认证，APK 下载也需要认证。

建议接口：

```text
GET /api/app-update?channel=release
GET /api/app-update/artifacts/{artifact_id}.apk
```

未配置发布时正常返回 `available:false`。旧后端不支持接口时，客户端将 404 解释为“服务器暂未提供应用更新”，不得导致登录或工作台报错。其他错误分别说明检查失败、会话过期等。

版本信息示例：

```json
{
  "available": true,
  "channel": "release",
  "version_code": 9,
  "version_name": "1.3.0",
  "package_name": "app.mydesk.android",
  "min_sdk": 26,
  "artifact_id": "immutable-artifact-id",
  "apk_path": "/api/app-update/artifacts/immutable-artifact-id.apk",
  "size_bytes": 24000000,
  "sha256": "64位十六进制摘要",
  "published_at": "2026-10-07T12:00:00Z",
  "notes": "本版本更新说明"
}
```

示例版本不是强制值；实际从构建产物读取。使用 `version_code` 比较，不按版本字符串排序。必须检查设备系统版本兼容性。

发布产物与版本信息放在后端专用持久目录，不能在服务启动时从公网任意下载。容器部署应使用独立持久挂载，并在部署文档中说明。artifact_id 只映射服务器登记过的不可变文件，不直接拼接用户路径。读取清单应校验 schema、大小、版本号和路径；未完成上传的文件不能对客户端可见。

实现跨平台发布准备脚本，例如 `scripts/prepare_android_update.py`：接收已经完成签名的 APK 和更新说明，通过 Android SDK 工具读取真实包名、版本、minSdk，验证签名有效性，生成摘要和清单，输出可部署的目录。不要让操作者手填可能与 APK 不一致的版本号。发布使用临时目录＋原子切换清单；新清单发布前 APK 已完整就位。旧版本产物保留一段时间，避免旧下载链接在新版本发布时失效。

区分 release/debug 渠道，APP 只查询对应渠道。发布方提供该渠道预期签名证书指纹并验证一致性；不因云端缺少正式签名而把 debug APK 标成 release。常规用户只需要正式渠道，调试渠道用于开发验收。

### 4.3 下载、完整性和生命周期

- 延用现有 HTTPS 校验和会话，禁止任意跨域下载及携带 cookie 跳转外站。`apk_path` 必须符合预期的同源固定路由。
- 流式下载到 APP 私有目录，设置超时、最大大小和合理磁盘空间检查；不得把 APK 一次读入内存。建议上限 200 MiB，并以实际包体复核。
- 下载到临时文件，完成后验证字节数和 SHA-256；只有验证通过才能切换为待安装文件。失败不能保留可安装状态。
- 解析 APK 包名、版本和系统要求，与清单一致，并确认是当前 APP 的更高版本。检查与当前安装签名兼容；本项目固定签名策略下可采用严格同签名，若未来支持证书轮换须显式实现。Android 系统安装器是最终签名验证者，不得绕过。
- FileProvider 只暴露更新专用目录中的目标 APK，授予临时读取权限；不能暴露整个私有目录。
- 生命周期：由 ViewModel/独立状态控制器管理，Compose 只显示状态和派发操作。避免用全局业务 busy 锁死其他页面。
- 用户退出、更换服务器、会话失效后取消该服务器相关更新操作并丢弃过期结果，不能安装另一个账户/服务器的残留下载。
- 单个更新任务去重；页面重组、旋转、反复点击不得开启并发下载。首次打开若发现下载中断的临时文件，应清理或安全重试。

### 4.4 版本与后端兼容

这些功能需要同时更新后端和客户端。优先部署向后兼容的后端，再提供新版 APK。新 APP 接旧后端时，不能把“随机已开启”显示成有效、但实际由旧后端按固定增量执行。可在快照或能力接口增加显式能力标志；缺少对应能力时，关闭相关新操作并显示需要升级服务器。

同理，没有 webhook 收件箱接口时，展示未支持状态，而不是把接口错误当成空收件箱。旧客户端连接新后端时仍能执行既有任务。

### 4.5 必须验证

- 相同/旧版本不提示更新，版本号比较正确，未配置/离线/旧后端可用。
- 错误大小、摘要、包名、版本、签名、系统版本，截断文件和磁盘错误均不能进入可安装状态。
- 重定向及跨域链接被拒绝；鉴权失败不把 JSON 错误响应当 APK。
- 下载中旋转、双击、退出登录、更换服务器；授予安装权限后继续安装。
- 服务端 APK 下载鉴权、路径穿越、不可变产物、发布中途失败，以及新版本发布不破坏旧下载。
- 真机最终验收：从同签名旧版覆盖更新，保留设置、会话、提醒、数据库及待同步操作。云端无手机时明确标为待验收。

## 5. 飞书格式通知接收

### 5.1 范围与消息流

```text
通知发送方 ──→ 原飞书 webhook ──→ 飞书群
          └──→ MyDesk 接收地址 ──→ 后端保存 ──→ APP 收件箱 / 原生通知
```

发送方支持多个地址，沿用两份投递；MyDesk 不保存飞书 webhook 地址、不向飞书转发，也不尝试从飞书 webhook 读取历史。此功能不接飞书群聊事件，不执行消息中的命令。

接收接口由后端提供，不能把手机当公网 HTTP 服务器。发送方必须能够访问 MyDesk HTTPS 地址。双发需要发送工具允许自定义目标地址；若其飞书通道硬编码了域名，接入文档给出通用 HTTP 请求或脚本示例，不声称只改地址就一定兼容所有工具。

### 5.2 来源与接收地址

设置新增“通知接入”，支持创建来源、重命名、启用/停用、查看最近接收状态、重置接收密钥和删除来源。名称示例：服务器告警、签到结果。

建议接口：

```text
GET    /api/notification-sources
POST   /api/notification-sources
PATCH  /api/notification-sources/{id}
POST   /api/notification-sources/{id}/rotate-secret
DELETE /api/notification-sources/{id}
POST   /api/incoming/feishu/{source_id}/{secret}
GET    /api/inbox?limit=50&before=<cursor>&source_id=<optional>
POST   /api/inbox/read
```

管理、列表和已读操作必须有会话，写操作保留 CSRF。只有最后的外部接收接口采用来源密钥认证；认证中间件只豁免严格对应的接收路由，不能扩大整个 API 的匿名访问范围。现有 `/api/webhook/{secret}` 继续处理原任务结果，不做复用。

每个来源生成至少 32 字节加密安全随机密钥。数据库存密钥摘要，创建和重置时只返回一次完整地址；界面允许立即复制，之后说明如需重新获取地址应重置。重置后旧地址立即失效。来源不存在返回 404，密钥无效或来源停用返回 401/403，响应不暴露配置细节。第一版采用路径密钥即可满足 CPE 协议，不强制再实现 Bearer Token；CPE 配置中的 headers 可以为空。若实现 Bearer 模式，需明确每个来源选用的鉴权方式，不以“任一凭据碰巧通过”绕过已配置的更严格认证。

CPE 示例路径 `/api/integrations/cpe/YOUR_RANDOM_KEY` 只是建议形态，协议允许自行决定路径。使用统一的 `/api/incoming/feishu/{source_id}/{secret}` 即可，配置时完整复制到 CPE 的 url；无需为两个名称重复实现接收器。接口必须直接返回 JSON，不允许 302 跳登录页或跳其他地址；HTTPS 证书应能通过 CPE 系统 CA 校验。

拼接复制地址时使用已配置的可信服务地址或 Android 当前连接地址，不盲信外部 Host/转发头；只信任项目原有明确配置的反向代理。日志不得记录完整密钥路径，部署说明也要提供代理访问日志脱敏建议。

删除来源前确认；建议软删除并保留历史消息及当时来源名称。删除/停用后不再接收新消息，不追溯删除原消息。

### 5.3 支持的消息格式

第一版必须完整支持纯文本 `msg_type=text` / `content.text`，无需飞书卡片、富文本、事件订阅和交互回调。为后续扩展保留解析器分层即可，不提前实现未使用的复杂结构。

纯文本示例：

```json
{
  "msg_type": "text",
  "content": {"text": "📱 短信通知\n发送方: CPE 测试发送方\n内容: 【示例】验证码 123456，这是测试短信。\n时间: 2026-10-07 20:00:00 +08:00"}
}
```

UTF-8、中文、emoji、换行和引号需要原样保存；不强制 trim 或重组正文。发送号码、短信内容和短信接收时间都在 text 中，正文时间按发送方约定为北京时间 +08:00。服务器另外记录自己的接收时间，不用正则猜测结果覆盖原文。号码/验证码/时间提取不作为本次必需功能或接收成功条件。

不要读取文中的指令来触发任务，也不加载任意 HTML/WebView。链接仅允许安全的 http/https 地址，经用户点击后在浏览器打开。图片、附件、卡片及其他不支持结构返回明确 400，不能忽略负载后返回成功。

兼容发送方附加的飞书 `timestamp`、`sign` 字段，但它们不作为 MyDesk 鉴权依据；MyDesk 以自身来源密钥认证。不要假装通过了飞书签名验证。

完成数据库持久化后必须返回 HTTP 200、JSON 数字 code=0；采用 CPE 协议的最小成功响应：

```json
{"code":0,"msg":"success"}
```

重复请求也返回上述相同成功响应。不得使用 `{"accepted":true}`、HTTP 204、空正文或字符串 `"0"` 代替。错误返回适当 HTTP 状态和非零 code、可读 msg：格式 400，鉴权 401/403，请求过大 413，限流 429，临时存储失败 500。

参考协议说明 CPE 对超时、非 HTTP 200、无效 JSON、缺少成功码或非零成功码都会保留待发记录，下轮重试。当前约定检查间隔 180 秒、请求超时上限 20 秒，因此接收接口应在数秒内完成入库并响应，不能等待 FCM、手机在线或其他外部请求。实际兼容性要包含协议中的完整样本。

### 5.4 持久化、去重与限制

新增独立通知表，不写入 tasks、不借用步数记录。建议包含内部消息 ID、稳定分页序号、source_id、来源名快照、标题、完整正文、消息类型、服务端接收时间、已读时间、幂等标识。发送方的 64 位 ID 与内部消息 ID 分别保存，推送继续使用项目原有通知事件 ID，不能把 64 位 ID 直接塞进只接受 32 位事件 ID 的 Android 协议字段。可以保存受请求大小限制的原始负载，但不记录凭据、不向无权限接口暴露；短信正文和验证码不得进入普通诊断日志。

按 CPE 协议使用标准请求头 `Idempotency-Key`，值为 64 位小写十六进制字符串。为“CPE 短信”来源强制要求该字段并校验；创建来源时可以区分 CPE 与通用文本来源，通用来源没有 ID 时每次成功请求视为独立消息。无需为了本次对接额外要求 `X-MyDesk-Event-Id` 或顶层 event_id，也不要要求 CPE 修改现有正文。

数据库为 `(source_id, idempotency_key)` 建唯一约束。先鉴权与校验格式，再判重。该 ID 已存在时，按发送方协议直接返回相同成功响应，不新建消息、推送任务或修改原文；即使重试负载内容不同也保留第一次已接收的记录，可记录不含正文的冲突诊断，不改变协议的成功应答。不同来源可使用相同 ID。

不要按“号码＋正文”在 MyDesk 端再次粗略去重。参考协议说明 CPE 已在每个目标内合并同号码、同正文、接收时间相差不超过 60 秒的重复记录，且为同一待发短信跨超时、检查轮次和重启沿用相同 ID。MyDesk 只负责幂等落库与不重复推送。

用数据库唯一约束和事务处理并发重复请求。为保证保留期后的重试行为清楚，幂等记录至少在消息保留期内有效，并在接入文档写明。

沿用 64 KiB 请求上限；由来源名/正文首行派生的标题最多 120 字符，APP 推送摘要最多 500 字符。持久化的 content.text 必须完整保留，不为满足推送限制而截断原文；列表和系统通知使用摘要，详情展示全文。超出可接收上限应明确拒绝，不返回成功。对结构做严格类型校验，防止异常负载造成资源耗尽。

每来源建议限制 60 次/分钟，返回 429 和 Retry-After；反向代理层可另设匿名异常请求限制。没有可靠代理配置时不信任请求自报 IP。

保留最近 90 天，设置总量上限（建议 10000 条）。清理时同时处理关联记录，来源和设置不随消息清理删除。列表默认 50 条、最多 100 条，按稳定序号倒序游标分页，支持来源筛选。普通通知不自动算作“需要处理”的异常。

### 5.5 APP 页面与同步

保持现有四个底部导航，不新增第五页。工作台在最近邮件之后增加“最近通知”，最多显示 3 条；无来源、无消息时可隐藏，设置里仍能找到接入入口。

列表展示来源、标题、摘要、时间和未读状态；提供查看全部、详情、来源筛选、标为已读、全部已读。收件箱已读状态按现有单账号多设备模式在服务器统一保存，重复标记幂等。全部已读以用户看到的最新序号为截止，避免把操作过程中刚到达的新消息误标为已读。

前台沿用现有 WebSocket 快照更新；快照只附带最近少量消息和未读数，不能每条消息都传全历史。完整记录用分页接口获取。离线显示缓存，后端持续收消息，重新联网后补同步；已读操作优先复用现有离线操作队列，并验证服务端幂等与账号切换隔离。

Web 端至少同步提供来源管理和收件箱基础操作，避免设置只能在手机管理；可复用现有弹窗/详情交互，不重做整个工作台。

### 5.6 原生通知

新消息接入现有原生推送机制，建议新增独立 inbox 类型/渠道，名称为“外部通知”。同步更新后端事件构造、Android 白名单、通知渠道、详情定位、去重和点击逻辑，保留设备绑定、会话和有效期校验。

消息持久化成功是接收成功标准；推送失败不应让发送方反复发送已经入库的消息。按 CPE 协议优先在同一数据库事务中登记消息与通知待办，提交后才返回成功；若现有结构不便直接写原生事件表，可原子写持久派发待办，由后台再生成原生事件，生成过程也必须幂等。不能只从快照最近 3/20 条抓新消息，否则突发到达或重启会漏通知。复用原有 outbox、重试及过期规则，不无限积压过期锁屏通知。

推送未配置时，收件箱仍可使用，设置中明确显示“消息可同步，后台推送未配置”。点击通知进入对应消息详情；已删除/清理消息时给出提示并进入收件箱。新旧客户端推送能力不同的情况下应做能力区分或确保旧端安全忽略，不破坏原有提醒渠道。

### 5.7 必须验证

- 协议的纯文本样本完整保存；中文、emoji、换行、引号和正文时间不丢失；未知类型和超限数据报错。
- 缺失/失效密钥、来源停用、重置、删除、限流、请求大小、鉴权及 CSRF。
- 并发幂等：同来源同 Idempotency-Key 仅一条消息和一个通知待办；不同来源可使用同 ID；CPE 缺失或非法 ID 拒绝；通用文本来源无 ID 可重复。同 ID 改变内容仍成功应答且不覆盖首条。
- 成功必须为 HTTP 200 与数字 code=0，不能把字符串/布尔值当成功码；模拟“已提交事务但响应丢失”后重试，确认不重复入库/推送。
- 重启后消息仍在；稳定分页不漏不重；来源筛选及保留清理正确。
- 已读跨设备一致，全部已读不吞新消息，离线已读重试安全。
- 普通通知不污染任务、步数或异常列表；旧 webhook 的已有测试保持通过。
- 推送失败不丢消息，不因快照窗口漏事件，不重复提醒；点击定位、旧消息清理、注销后旧通知均正确处理。

### 5.8 CPE 接续配置与责任边界

参考协议提供了发送端接续步骤，本次云端只实现 MyDesk 端并编写联调说明，不连接或修改 CPE、电脑代理和真实私有配置。

- MyDesk 就绪后，创建“CPE 短信”来源并复制 HTTPS 地址。CPE 私有配置中的 url 填该地址，使用路径密钥时无需额外 Authorization。
- `enabled_at` 需要在实际启用时填写当前 UTC 时间，不能把文档示例日期当作真实启用时间。参考协议规定：首次启用跳过更早的历史短信；同 URL 暂停再启用沿用状态，修改 URL 会重建基线。因此重置 MyDesk 接收密钥会改变 URL，联调说明必须提醒同时检查启用时间，避免漏接切换期间的短信。
- CPE 端飞书与 MyDesk 保持独立成功记录；MyDesk 收到或重试失败，不应修改飞书通道。
- 电脑代理需要将 MyDesk 域名和 HTTPS 端口纳入已有目标白名单；白名单不保存完整接收地址或密钥，是否重启代理按发送方文档执行。
- 参考文档描述 CPE 的第二目标源码尚未部署、真实 MyDesk 地址尚未配置；不要把这个描述当作当前设备状态，正式接续时核实。
- 参考文档说明手机已有 Google 服务，但公开 APK 没有个人 Firebase 配置；须在真实环境验证，不能凭这一描述宣称 FCM 已可用。
- 最终联调至少覆盖：新短信双端收到；MyDesk 临时不可达而飞书成功；恢复后 MyDesk 补发；成功响应丢失后的幂等重试；服务器重启；手机离线后补同步与后台通知。

## 7. 最终完成标准

- 配置随机 80±10% 后，正常追加量在 72～88 范围内，固定模式行为不变；重启/失败不改变已确定值，结束和上限正确。
- 同签名新版发布后，APP 能发现、下载、校验并调起系统安装；安装前后数据保持；没有版本、服务器过旧或下载失败时可恢复。
- 一份通知分别发到飞书和 MyDesk，MyDesk 后端可靠保存，APP/Web 可看详情和已读；有有效推送环境时完成通知展示和点击定位。
- 现有提醒、步数手动提交、任务历史、GitHub 接入、账户与离线操作不回归。
- 自动化通过与真机待验收分开报告，不能用其中一项代替另一项。
